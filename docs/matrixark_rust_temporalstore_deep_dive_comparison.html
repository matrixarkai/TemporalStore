Rust TemporalStore Deep Dive

Storage engine internals, MatrixArk context workflow, and a direct comparison with the C++ TemporalStore implementation.

Summary Source Map Storage Model Write/Read Paths Cache Lifecycle Context Rust vs C++ Gaps

Executive Summary

Rust TemporalStore is no longer just a client or proxy shell. The core runtime has a real storage engine made of TemporalEngine, slot-first indexes, page/block address aliases, packed timestamp pages, a write-ahead log, a multi-layer cache, storage lifecycle reports, and data-node schedulers. MatrixArk context records are stored on the same engine primitives as other data models: model maps point to PageAddress values, timestamped maps point to packed pages, and context-specific retrieval uses engine commands plus workflow code.

The deepest Rust storage engine code currently lives in crates/temporalstore-rust/src/engine.rs, engine/state.rs, engine/context.rs, engine/packed_pages.rs, block_store.rs, cache.rs, wal.rs, and data_node.rs.

The C++ engine remains the mature reference for tightly packed page indexes, coroutine-driven StorageManager, page GC, page compaction, zones, stream/blob rollover, and production path behavior. Rust has caught up on public contract shape and much of the runtime machinery, but it still carries more report scaffolding and compatibility aliases, and its page/block layer is less compact than the C++ packed structures.

Rust Storage Model

1. Engine owns loaded shards

TemporalEngine stores loaded shard state in Arc<RwLock<HashMap<ShardId, ShardState>>>. A command first resolves the shard, validates admission and readonly state, then executes against the in-memory model maps and page store.

2. Model maps point to pages

ShardState keeps maps such as strings, hashes, sets, features, sequences, IPS, risk, and context records. Most values are not stored inline; they point to PageAddress, which is currently an alias for BlockAddress.

3. Slot index is the runtime authority

CoreIndex contains a SlotMap. Each SlotNode records object ids, deleted object ids, dirty generation, in-memory/loading flags, TTL, and a PageIndexMap. The shape mirrors the C++ Index -> SlotMap -> SlotNode -> PageIndex/ObjectIndex hierarchy, but uses Rust maps rather than packed structs.

4. Pages are durable segments

LocalBlockStore appends encoded page records and returns BlockAddress. The public page-store compatibility module reexports BlockAddress as PageAddress and LocalBlockStore as LocalPageStore, so newer code can use canonical block names while older engine code still compiles with page-store terms.

Write And Read Paths

Rust write path

ExecuteRequest
  -> TemporalEngine::execute_with_storage_override
  -> shard lookup and admission
  -> validate command preconditions
  -> execute_on_shard(cache, page_store, async_storage, command)
  -> append value/page through LocalPageStore alias
  -> update model map and slot-first index
  -> mark dirty_objects
  -> if sync durable:
       wal_store.append(command)
       index_log_store.append_json(serialized ShardState)
       persist index bytes

In Rust, the loaded ShardState is both the current logical object index and the source for rebuilding secondary views. The promote_model_maps_to_slot_index_authority and reconcile_secondary_views_from_slot_index calls keep the slot-first index and model maps aligned.

Rust read path

Command query
  -> model map lookup or slot_index_page_address
  -> PageAddress / BlockAddress
  -> read_page_bytes(cache, page_store, shard_id, address)
  -> MultiLayerCache get/refill or LocalBlockStore read
  -> decode bytes into object, feature point, or ContextWire value
  -> filter by timestamp/status/kind/score where needed

Timestamped models use BTreeMap<u64, PageAddress>. For packed timestamp pages, several logical timestamps can point to the same durable page. read_feature_point_cached keeps a per-query decoded page cache so repeated reads from the same packed page avoid repeated JSON decode.

Cold scan path

Cold timestamp/page range
  -> page index scan
  -> no-cache page read
  -> bounded decode
  -> no hot-cache promotion

The canonical cold-scan contract is defined in engine/reports.rs and exposed through storage_cold_scan_contract. The Rust runtime has the TS_COLD_SCAN_NO_CACHE_FILL knob and report fields such as cold_scan_no_cache_reads and hot_cache_promotions. The intended production invariant is that temporal compression or GC scans do not warm serving cache unless a user-facing retrieval explicitly asks for raw evidence.

Multi-Layer Cache

Rust's MultiLayerCache is a real tiered cache, not just a map. It contains memory and pmem maps, an SSD/disk index, pin tracking, an access order, async writeback queue, admission metadata, and detailed stats.

Layer/FeatureRust implementationWhy it matters
Memory object cache memory: HashMap<CacheKey, Arc<[u8]>>, byte capacity, access order Fast hot-page path; evicted under memory pressure.
Persistent-memory style tier pmem map, pmem capacity, pmem order Intermediate warm tier before disk.
Disk block cache disk_index, disk order, encoded cache blocks Durable-ish read-through fallback for cache misses.
Async writeback async_writeback_queue, queue limit, drain report, rejection counter Backpressure evidence for production write path.
Invalidation invalidate, invalidate_memory_only, shard/slot invalidation helpers Append/compaction watermark changes can prevent stale page hits.
Pinning get_pinned_handle, pin, unpin Protects active readers during page lifecycle operations.
Rust is strong here because cache behavior is visible in code and metrics: memory hits, disk hits, refills, invalidations, async writeback queue depth, writeback rejections, compressed hits, and zero-copy handle hits.

Storage Lifecycle And StoreManager

The Rust lifecycle path is split between TemporalEngine and DataNodeRuntime. The engine computes lifecycle plans and can apply them. The data node owns schedulers and runtime reports for dirty dumps, expiry sweeps, storage lifecycle, and storage manager cycles.

Rust lifecycle plan

storage_lifecycle_plan(request)
  -> slot_storage_summaries
  -> dirty slots and undumped WAL records
  -> live page segment ids
  -> stale page segment ids
  -> recovery report and reclaim candidates
  -> delayed-destroy segments
  -> page GC dependency plan
  -> follower cursor / snapshot retention checks
  -> lifecycle reasons and selected dump slots

Rust storage manager cycle

run_storage_manager_cycle(request)
  -> prepare
  -> expire
  -> page reclaim guarded by dependency plan
  -> apply lifecycle
  -> eviction
  -> WAL/index-log reclaim
  -> index GC
  -> page compaction
  -> metrics reap
  -> StorageManagerCycleReport

The cycle intentionally keeps a C++ stage order in the report: prepare, reclaim_oplog, expire, evict, reclaim_page, index_gc, compact, reap_metrics. The canonical public contract maps these to the broader parity phase names: prepare, reclaim, evict, expire, page_gc, block_gc, compaction, index_gc, delayed_destroy, follower_cursor_safety, and watermark_progress.

Physical reclaim semantics

Rust distinguishes cache eviction from physical reclaim. Eviction removes cache entries and optionally drops cold objects under policy. Physical reclaim is gated by storage_page_gc_dependency_plan, which refuses reclaim when live page refs, slot dump manifests, shared-store replay cursors, snapshot refs, checkpoint floors, Raft install floors, or delayed-destroy grace periods still retain a segment.

This is the right semantic model, but C++ still has the more mature production background loop and compact packed metadata. Rust has strong reporting and explicit dependency checks; the remaining parity work is proving the same behavior under long-running live load, restart, follower cursor, and compaction scenarios.

MatrixArk Context On Rust TemporalStore

Context management uses normal TemporalStore primitives. In ShardState, context records are stored as separate maps:

  • context_nodes: HashMap<String, PageAddress>
  • context_events: HashMap<String, BTreeMap<u64, PageAddress>>
  • context_indexes: HashMap<String, BTreeMap<u64, PageAddress>>
  • context_children: HashMap<String, BTreeMap<u64, PageAddress>>
  • context_embeddings, context_summaries, context_compressions, context_entities

Context events are timestamp-keyed with a fanout disambiguator: 

context_timeline_key(timestamp_ms, disambiguator)
  = timestamp_ms * CONTEXT_TIMELINE_FANOUT
    + (disambiguator % CONTEXT_TIMELINE_FANOUT)

That means several events created from the same agent message do not overwrite each other as long as their event ids differ. context_event_timeline_key_for_write searches the timestamp fanout window and either finds the existing event or chooses a free timeline slot.

Rust context retrieval

ContextRetrieveRequest
  -> require tenant_hash and node_hashes
  -> embed query
  -> query summary embeddings for node_l0/node_l1 refs
  -> reorder node traversal by summary score
  -> fetch ContextNode
  -> fetch ContextEvent time range
  -> secondary-index/lexical prefilter debug
  -> rank blocks by relevance, tier, event time
  -> return ContextRetrieveReport

ContextInjectRequest
  -> retrieve_context
  -> token-budget select blocks
  -> emit compact prompt and ContextPackAudit

Rust has the key native behavior needed to keep Python thin: query understanding, summary embedding traversal, context-event filtering, ordering, injection, and audit assembly live in Rust workflow code. The main difference from the C++ path is product shape: Rust exposes this through the Rust library/proxy workflow today, while C++ has a native extension/API surface tied to the existing C++ server and SDK.

Practical Gaps And Next Fixes

Rust gaps to close against C++

  • Make public reports use canonical names only, with compatibility aliases kept out of parity gates.
  • Keep reducing string-heavy Rust PageIndex/SlotNode reports for hot paths; compact structs should be used internally for native retrieval.
  • Run longer live storage lifecycle loops to prove WAL reclaim, index GC, delayed destroy, compaction and follower-cursor safety under restart and load.
  • Prove cold scan no-promote behavior with real page/block reads, not just report fields.
  • Move more Raft and membership implementation into the standalone RustRaft library while TemporalStore consumes it as a dependency.

C++ gaps to close against Rust

  • Normalize reports to the Rust-style canonical storage contract so comparison tools see identical shapes.
  • Make C++ context retrieval return non-empty, logically equivalent selected refs before treating latency as meaningful.
  • Use placement/index/cache driven fetch for context, avoiding broad scan/score paths.
  • Add native candidate cache and compact ContextPack assembly parity with Rust workflow behavior.

Most important parity gate

Same corpus + same storage mode + same topology + same config
  -> Rust and C++ expose the same public storage contract
  -> page/block indexes rebuild after restart
  -> cache eviction != physical reclaim
  -> cold scan does not warm hot cache
  -> context retrieval selected refs are non-empty and equivalent
  -> latency/QPS comparison is allowed only after correctness passes
