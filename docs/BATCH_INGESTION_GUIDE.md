# Batch ingestion of skills — customer guide

How to load a collection of skill documents (playbooks, specification docs, test-result JSON) into
MatrixArk: all at once, one at a time, or resumed after an interruption — and how to watch it while
it runs.

Everything here uses `tools/matrixark_batch_ingest.py`, which ships with the product. It has no
dependencies beyond the Python standard library.

---

## 1. Quick start

```bash
# see what would be sent, without sending anything
python3 tools/matrixark_batch_ingest.py --dir ./playbooks --dry-run

# ingest them
python3 tools/matrixark_batch_ingest.py --dir ./playbooks \
    --base-url https://your-host:8080 --user-id acme_team
```

`--dir` walks the directory recursively and picks up `*.md`, `*.markdown` and `*.json`. Documents are
sent in sorted order, so two runs over the same directory process files in the same sequence.

---

## 2. Three ways to provide the skill list

**A directory.** Simplest when your playbooks already live in one tree.

```bash
python3 tools/matrixark_batch_ingest.py --dir ./playbooks
python3 tools/matrixark_batch_ingest.py --dir ./playbooks --glob '*.md'      # narrow it
python3 tools/matrixark_batch_ingest.py --dir ./playbooks --glob '*.md' --glob '*.json'
```

**A manifest file.** Best when the list is curated, generated by another system, or a subset of a
larger tree. One path per line; blank lines and `#` comments are ignored.

```
# skills.txt
playbooks/acme/checkout.md
playbooks/acme/returns.md
playbooks/globex/pricing.json
```

```bash
python3 tools/matrixark_batch_ingest.py --manifest skills.txt
```

The manifest also accepts JSON Lines, so you can generate it from a database or a spreadsheet export:

```
{"path": "playbooks/acme/checkout.md"}
{"path": "playbooks/globex/pricing.json"}
```

**Explicit paths.** For one document, or a handful:

```bash
python3 tools/matrixark_batch_ingest.py playbooks/acme/checkout.md
```

The three sources combine, and duplicates are removed, so `--dir` plus a `--manifest` of extras
works as expected.

---

## 3. One at a time, or many at once

`--concurrency` sets how many documents are in flight. The default is `1` — strictly one at a time.

```bash
--concurrency 1     # one by one (default); gentlest, easiest to reason about
--concurrency 4     # four in flight; good general choice
```

Higher is not automatically faster. Ingest work is CPU-bound on the server, so beyond roughly the
number of cores available to the service you are queueing, not parallelising. On a 4-vCPU box with a
co-resident encoder, `--concurrency 4` is a sensible ceiling.

## 4. Watching it run

Progress prints as each document completes:

```
  [37/500] ok=36 failed=1 skipped=0 1.42/s eta=326.1s
```

For a dashboard, a monitoring agent, or another process, `--status-file` writes the same numbers as
JSON on every update:

```bash
python3 tools/matrixark_batch_ingest.py --dir ./playbooks \
    --status-file /var/run/ingest-status.json
```

```json
{"total": 500, "done": 36, "failed": 1, "skipped": 0, "remaining": 463,
 "bytes": 47563008, "elapsed_s": 25.4, "docs_per_s": 1.42, "eta_s": 326.1, "running": true}
```

The file is written atomically, so a reader never sees a half-written document. `running` flips to
`false` when the run finishes — poll for that rather than watching the process.

```bash
watch -n 5 'cat /var/run/ingest-status.json | python3 -m json.tool'
```

Use `--quiet` to suppress the terminal lines and rely on the status file alone, which is what you
want under a scheduler or in a log-sensitive environment.

## 5. Interrupting and resuming

Ingest is a **keyed upsert**: each document carries a stable `identity_key` derived from its path, so
re-ingesting the same document replaces the previous version rather than creating a duplicate.
**Re-running the whole batch is always safe.** You never need to track where you stopped in order to
avoid corrupting data.

That makes resuming purely an optimisation — skipping work already done:

```bash
python3 tools/matrixark_batch_ingest.py --dir ./playbooks \
    --state .ingest-state.json --resume
```

The first run records each completed document in the state file. On a later run, `--resume` skips
those and reports them as `skipped`. Without `--resume`, everything is re-sent (harmless, just
slower). A corrupt or missing state file is ignored rather than fatal, for the same reason.

To force a full re-ingest after editing your playbooks, delete the state file — or simply drop
`--resume`.

---

## 6. Updating a playbook

Edit the document and ingest it again. Because the `identity_key` is the same, the new version
replaces the old one; there is no delete step and no window where both versions are live.

If you move or rename a file, its identity changes with its path — the old entry remains until you
remove it explicitly. Prefer editing in place over renaming for documents already in the store.

## 7. Authentication

The API key is read from an environment variable, never passed as an argument, so it cannot appear
in shell history or in `ps` output:

```bash
export MATRIXARK_API_KEY='...'
python3 tools/matrixark_batch_ingest.py --dir ./playbooks
```

To read it from a differently named variable:

```bash
--api-key-env ACME_PROD_KEY
```

Defaults can also come from the environment: `MATRIXARK_BASE_URL` and `MATRIXARK_USER_ID` are used
when `--base-url` and `--user-id` are not given.

## 8. Confirming the result

List what landed, then retrieve against it:

```bash
curl -s -X POST http://your-host:8080/v1/memories \
     -H 'Content-Type: application/json' \
     -d '{"user_id":"acme_team"}'

curl -s -X POST http://your-host:8080/v1/retrieve \
     -H 'Content-Type: application/json' \
     -d '{"query":"how do I apply the coupon at acme-store checkout","user_id":"acme_team"}'
```

Retrieval returning your content is the real check. A successful HTTP status only means the document
was accepted.

## 9. Confirming the deployment is configured correctly

Before a large import, verify the deployment is talking to the models you expect:

```bash
curl -s http://your-host:8080/v1/admin/config -H "Authorization: Bearer $MATRIXARK_API_KEY"
```

```json
{"extraction": {"provider": "openai_compatible", "model": "deepseek-chat",
                "api_key_env": "DEEPSEEK_API_KEY", "api_key_configured": true},
 "embedding":  {"provider": "openai_compatible", "require_model_embeddings": true},
 "warnings": []}
```

**Check `warnings` is empty.** It is not cosmetic. Both extraction and embedding fall back to a
local deterministic path when they are not configured, and that path answers with `200 OK` — a
misconfigured deployment looks healthy from the outside while storing hash vectors and rule-extracted
text. The warnings name exactly that situation.

Key values are never returned by this endpoint; it reports the *name* of the environment variable
holding each key and whether it currently resolves.

## 10. What to expect

Measured on 1,000 markdown/JSON documents averaging 1.3 MB, on the storage path:

| | |
|---|---|
| Throughput | ~1.3 s per document, flat as the corpus grows |
| 1,000 documents | ~23 minutes |
| 10,000 documents | ~4 hours |
| Memory | ~1.35 GB resident per 1,000 documents |
| Disk | ~4.6 GB per 1,000 documents after reclaim |

Per-document cost does **not** grow with the size of the store, so timings scale linearly — a corpus
ten times larger takes ten times as long, not longer.

Two caveats worth planning around:

- Small documents are dominated by fixed per-request cost, so documents-per-second is much lower for
  a few-KB playbook than the figures above suggest. Batch size, not document size, drives wall clock.
- If extraction is pointed at a hosted model, each ingest includes that call. Throughput then depends
  on your provider's latency and rate limits far more than on the store.

## 11. Troubleshooting

**`no input documents found`** — `--dir` matched nothing. Check the path, and remember the default
globs are `*.md`, `*.markdown`, `*.json`; anything else needs an explicit `--glob`.

**Failures at the end of a run** — the last lines list each failed document with its reason. Network
errors and timeouts are retried three times with backoff before being reported; a `4xx` is not
retried, because it will not improve. Fix the cause and re-run with `--resume` to retry only what
failed.

**`http 401`** — the key variable is unset or empty. Confirm with `echo ${MATRIXARK_API_KEY:+set}`.

**Ingest is much slower than expected** — check `/v1/admin/config` for warnings, confirm the server
is not competing with another heavy job, and reduce `--concurrency` if the server is saturated.
Queueing more work at a busy server makes wall-clock worse, not better.

**Documents ingest but retrieval finds nothing** — almost always the embedding provider silently
falling back to hash vectors. `/v1/admin/config` will say so in `warnings`. Set
`MATRIXARK_REQUIRE_MODEL_EMBEDDINGS=1` so the deployment fails loudly instead.
