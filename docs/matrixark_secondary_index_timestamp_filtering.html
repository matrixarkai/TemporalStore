MatrixArk Secondary Index Timestamp Filtering

This note explains the difference between the ContextEvent primary timestamp key and the timestamp copied into secondary-index postings. It also shows how query understanding should use secondary indexes to filter candidates before embedding similarity, sparse lexical scoring, and final ContextPack assembly.

Short answer: ContextEvent is ordered by ingestion/event time. Secondary-index rows also carry a timestamp, but that timestamp is the ordered posting key for an inverted index, not another primary event key.

ContextEvent Primary Key

A ContextEvent has a time-ordered key so events under a node or segment can be scanned chronologically.

context_event/{scope_key}/{node_hash}/{timestamp_key_ms}:{event_id_hash}

Example value:

{
  "text": "Alice approved the Project Aurora GPU purchase after finance review.",
  "event_type": "confirmation",
  "source_type": "message",
  "source_ref": "codex:debug-message-pdf-session:001"
}

The timestamp key is used for latest-first retrieval, time-window filtering, temporal compression windows, TTL/GC decisions after compression, and replay of a node or session timeline.

Secondary Index Posting Timestamp

A secondary index posting is a compact pointer from an index term to one or more candidate records or candidate nodes.

data_model index_name timestamp_key_ms ref_type ref_hashes node_hash
context_batch_commit event_type:confirmation 1782681920550 [] 2100209595829882121
context_batch_commit classification:batch_memory 1782681920550 [] 2100209595829882121

The first row means: at time 1782681920550, node 2100209595829882121 had batch memory related to confirmation events. Since ref_hashes is empty, this is a node/batch hint, not a direct event/chunk/entity ref.

Why Timestamps Repeat

One event, chunk, entity, skill section, or batch can produce several index terms. The timestamp repeats because each posting belongs to a different inverted list.

event_type:confirmation  -> 1782681920550:event_hash
source_type:message      -> 1782681920550:event_hash
keyword:gpu              -> 1782681920550:event_hash
keyword:approval         -> 1782681920550:event_hash

These implementation fields should not be included in the final ContextPack unless debug mode is enabled.

How Filtering Works

flowchart TD A["Raw query"] --> B["Query understanding"] B --> C["Scope filter"] C --> D["Secondary-index lookup"] D --> E["Node L0/L1 traversal"] E --> F["Fetch leaf candidates"] F --> G["Dense/sparse/time/business scoring"] G --> H["Token-budget pack"] H --> I["Compact ContextPack"]

Query understanding emits a small structured plan:

{
  "query_type": "fact_lookup",
  "secondary_filters": {
    "source_type": ["message", "resource"],
    "event_type": ["confirmation"],
    "resource_type": ["pdf"],
    "keyword": ["gpu", "approval"]
  },
  "temporal_window": {
    "mode": "latest"
  }
}

Retrieval first applies scope, then looks up postings, intersects or score-merges those postings, converts them into candidate nodes or refs, and only then runs dense/sparse scoring.

Concrete Examples

What did Alice approve about the GPU budget?

{
  "query_type": "fact_lookup",
  "secondary_filters": {
    "event_type": ["confirmation", "approval"],
    "keyword": ["alice", "gpu", "budget"],
    "source_type": ["message", "resource"]
  },
  "temporal_window": {"mode": "latest"}
}

Lookup event_type:confirmation, keyword:gpu, and keyword:alice, fetch candidate events/resource facts/chunks, then score and pack the best cited evidence.

Show the GPU approval PDF section.

{
  "query_type": "resource_evidence",
  "secondary_filters": {
    "source_type": ["resource"],
    "resource_type": ["pdf"],
    "unit_kind": ["pdf_page"],
    "keyword": ["gpu", "approval"]
  }
}

Lookup resource and PDF postings first, then score only candidate chunks.

Which skill handles replay?

{
  "query_type": "procedure",
  "secondary_filters": {
    "source_type": ["skill"],
    "skill_trigger": ["replay"],
    "skill_tool": ["matrixark_replay"]
  }
}

Lookup skill postings and pack only the relevant skill sections, not the whole skill bundle.

What Indexes Should Remain

Keep only high-signal, bounded indexes:

source_type
resource_type
unit_kind
event_type
entity_type
skill_trigger
skill_tool
relative_path
heading_slug
keyword

Disable or avoid low-selectivity defaults such as classification:new_event, classification:batch_memory, status:observed, always-active status flags, debug/provider fields, and full node path strings.

Production Storage Shape

The current debug table shows one row per visible posting. Production storage should use TemporalStore-native inverted lists:

secondary_index/{scope_key}/{data_model}/{index_name}/{timestamp_key_ms}:{ref_hash}

For node or batch hints:

secondary_index/{scope_key}/context_batch_commit/{index_name}/{timestamp_key_ms}:{node_hash}

The serving ContextPack should not include index timestamps, hashes, and node hints by default. They belong in debug/audit when enabled.

Recommended Cleanup

  1. Keep timestamp_key_ms as the primary order key for ContextEvent.
  2. Keep timestamp_key_ms in secondary postings only as the ordered index key.
  3. Do not include index timestamps, hashes, and node hints in ContextPack by default.
  4. Group debug rows by (data_model, index_name, timestamp_key_ms, node_hash) and show counts instead of every posting when possible.
  5. Cap secondary index terms per object with dynamic config.
  6. Remove low-signal index terms from default extraction/indexing.
  7. Push filtering into C++/Rust TemporalStore native APIs so Python does not materialize large posting lists.
Practical rule: if a field is useful for retrieval prefiltering, store it in ContextIndex. If it is useful for answering the user, store it in the source record or ContextPack. If it is useful only for debugging, store it in sampled audit/debug records.
