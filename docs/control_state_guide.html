TemporalStore · Control State

Frequency caps, quotas, pacing & risk — one serving primitive

Control State is TemporalStore's capability for fast-changing serving signals: counters, caps, quotas, pacing, eligibility, and suppression. One shape answers them all — read the current state, apply a rule, atomically update, return a decision.

read current state→ apply rule→ atomically update→ return decision

What you can build

Six use cases, one primitive

Each is a counter or piece of state under a time window or TTL. The atomic increment-then-read operator (HSETANDGET) does the accept-decision in a single round trip; the rest are queries and variations on the same key layout.

Frequency cap

Cap impressions per user

“Has this user seen campaign c123 more than 5× today?” Increment the daily bucket and allow while count ≤ limit.

HSETANDGET · window = calendar day
Tenant quota

Meter an API by tenant

Weighted increments against a daily allowance; allow while used ≤ limit, return remaining.

HSETANDGET · amount = request weight
Pacing

Spend against budget

Accrue spend, read spent-so-far, compare to target-by-now, then boost, dampen, or pause delivery.

HQUERY (read-heavy) + HSET
Suppression / risk

Detect a spike, suppress

Count failed logins over a rolling hour; suppress the moment the window crosses the threshold.

HSET (minute precision) + HQUERY range
Eligibility

Gate on combined state

Allow a promotion only if flags and counters match policy — a read that folds several control keys.

HQUERY + first/last (FOL)
Idempotent ingest

Replay-safe counting

Consume an at-least-once queue without double counting: a uuid dedups redeliveries inside a 5-minute window.

HSETANDGETOPT · uuid dedup

More controls, same primitive

Rate limit

Sliding-window throttle

“At most 100 requests per 60s per API key.” A rolling window at second precision, not a fixed calendar bucket.

HSETANDGETOPT · window = now−W … now
Concurrency

In-flight semaphore

Cap simultaneous jobs (e.g. 8 renders). Acquire increments, release decrements; over-capacity acquires roll back.

HSETANDGET +1 / CONTROLSTATEINCR −1
Debounce

Collapse bursts

Fire once things settle — one alert per incident, one email per sign-up burst. Any attempt refreshes the quiet window.

HSETANDGETOPT · limit 1 over quiet window
Distinct count

Unique-value sets

Unique devices per user per day, unique visitors per campaign — the change aggregator counts distinct values.

CONTROLSTATECHANGE + query change
Budget gate

Hard spend cap

Charge cost against a daily budget and stop at the ceiling; returns budget remaining. Idempotent with an event_id.

HSETANDGET(amount = cost)

The serving decision

How a frequency cap resolves in one call

The request builds a control key, the store atomically increments the window counter and returns the post-increment count, and the caller admits the event while it stays within the cap. The counter update and the read happen inside one command on one object, so concurrent requests can't slip past the cap.

Data model

Key design & value shape

A control key names the entity being controlled, the signal, and the window. Keep the value a single current state — not an append-only history — and let TTL reclaim expired windows.

# control:<tenant>:<entity>:<id>:<signal>:<window>
control:t1:user:u42:campaign:c123:impression:2026-07-24   # daily freq cap
control:t1:tenant:t1:quota:api_requests:2026-07-24         # tenant quota
control:t1:device:d7:login:failed:rolling_1h               # risk / suppression
// compact current-value state
{ "count": 4, "limit": 5, "window_start_ms": 1784880000000,
  "expires_at_ms": 1784966400000 }

How to use it

The command surface

Control State is a small, generic API. The Counter family holds counters and aggregates, Selection holds first/last values, Distinct holds distinct-value sets, and MANAGER handles admin. Everything is reachable over the Redis-compatible protocol and the typed Rust client.

Family naming. The families are Counter / Distinct / Selection (formerly H / Cpc / Fol). The RESP verbs carry both spellings — HSET*/COUNTER*, CPC*/DISTINCT*, FOL*/SELECTION* — and either works.
OperationRESP verbDoes
Increment (windowed)HSET / COUNTERSETAdd to the counter for a precision bucket at an occur-time.
Query windowHQUERY / COUNTERQUERYAggregate the counter over one or more windows.
Atomic incr-then-readHSETANDGET / COUNTERSETANDGETThe accept-decision primitive: bump the counter and return the window total in one command.
Atomic + optionsHSETANDGETOPT / COUNTERSETANDGETOPTSame, plus precision, TTL, and uuid idempotency for replay-safe ingest.
Distinct setCPCSET / DISTINCTSET · CPCQUERY / DISTINCTQUERYTrack distinct values (e.g. unique devices) with the change aggregator.
First / lastFOLSET / SELECTIONSET · FOLQUERY / SELECTIONQUERYKeep the earliest or latest value by occur-time.
AdminCONTROLSTATEMANAGERQuery, list fields, counts, and GC of control state.

Aggregators

sum/count total the increments · events counts buckets · min, max, first, last pick a value · change returns the distinct count over the window.

Worked examples

Each use case, end to end

1 · Frequency cap — atomic accept-decision

# RESP: bump today's bucket, read the day window, decide client-side
> HSETANDGET control:t1:user:u42:campaign:c123:impression:2026-07-24 \
      1784880000000 1  1784851200000 1784937599999  sum
(integer) 5      # count_after — allow while ≤ 5, else block
// Typed Rust client — one atomic call returns the post-increment count
let count = client.control_state_family_set_and_get(
    ControlStateFamily::H,
    "control:t1:user:u42:campaign:c123:impression:2026-07-24",
    occur_ms, /*amount*/ 1, day_start_ms, day_end_ms, "sum")?;
let decision = if count <= cap { Allow { remaining: cap - count } } else { Block };

2 · Tenant quota

# weighted increment; allow while used ≤ limit, surface remaining
> HSETANDGET control:t1:tenant:t1:quota:api_requests:2026-07-24 \
      <now_ms> <weight>  <day_start> <day_end>  sum
(integer) 483221   # remaining = 1_000_000 − 483221

3 · Campaign pacing — read-heavy

# accrue spend on delivery, then read to compute the pace multiplier
> HSET   control:t1:campaign:c9:pacing:spend:2026-07-24 <now_ms> <cost> sum
> HQUERY control:t1:campaign:c9:pacing:spend:2026-07-24 <day_start> <day_end> sum
(integer) 1300     # spent=1300 vs target_by_now=1500 → under pace → boost 1.12×

4 · Rolling-window suppression

# record a failed login at minute precision, count the rolling hour
> HSET   control:t1:device:d7:login:failed:rolling_1h <now_ms> 1 sum   # precision = 60s
> HQUERY control:t1:device:d7:login:failed:rolling_1h <now-1h> <now> sum
(integer) 5   # ≥ threshold → suppress (fires at exactly the 5th failure)

5 · Idempotent ingestion (replay-safe)

When events arrive from an at-least-once queue, pass a stable uuid. A redelivery inside the dedup window is a no-op write that still returns the current total, so the enforced count equals the number of distinct events — not deliveries.

# HSETANDGETOPT key ts amount start end agg  precision_ms ttl_ms uuid
> HSETANDGETOPT control:t1:user:u42:campaign:c123:impression:2026-07-24 \
      <ts> 1 <day_start> <day_end> sum  86400000 86400000 evt-9f3a
(integer) 5
> HSETANDGETOPT …same evt-9f3a…            # redelivered
(integer) 5    # deduped — no double count
// Typed client: precision + TTL + uuid in one atomic, idempotent call
client.control_state_family_set_and_get_with_options(
    ControlStateFamily::H, key, ts, 1, day_start, day_end, "sum",
    /*precision_ms*/ Some(86_400_000),
    /*ttl_ms*/      Some(86_400_000),
    /*uuid*/        Some("evt-9f3a".into()))?;

Client SDK

Production Python client

A dependency-free (stdlib-only) client speaks the RESP protocol above and wraps every use case in a typed method. It ships a thread-safe connection pool, a retry policy that respects at-most-once write semantics, UTC-correct windows, and a metrics hook — sdk/python/temporalstore/control_state.py.

from temporalstore.control_state import ControlState, ControlStateConfig

cs = ControlState(ControlStateConfig(host="127.0.0.1", port=16379, tenant="acme"))

# 1 · frequency cap — atomic accept-decision
d = cs.frequency_cap(user_id="u42", campaign_id="c123", limit=5)
if d.allowed: serve_ad()          # d.remaining impressions left today

# 2 · tenant quota   3 · pacing   4 · rolling suppression
cs.tenant_quota(resource="api_requests", limit=1_000_000, weight=3)
cs.record_spend(campaign_id="c9", cost=1300); cs.pacing(campaign_id="c9", budget=5000, target_by_now=1500)
cs.rolling_suppression(entity_kind="device", entity_id="d7", signal="login:failed", threshold=5)

# 5 · idempotent ingest (at-least-once queue)
cs.ingest_impression(user_id="u9", campaign_id="c1", limit=5, event_id=evt.id)

# 7 · sliding-window rate limit   9 · concurrency semaphore
cs.rate_limit(name=f"apikey:{k}", limit=100, window_ms=60_000)
with cs.concurrency_slot(resource="pdf-render", limit=8) as slot:
    if slot.allowed: render()

# 8 · debounce   10 · distinct count   11 · hard budget gate
cs.debounce(name="alert:svc-x", quiet_ms=60_000)
cs.add_unique(subject="user:u42:devices", value=device_id); cs.unique_count(subject="user:u42:devices")
cs.budget_gate(budget_id="camp:c9", cost=1300, budget=5000, event_id=evt.id)

Every method returns a typed Decision (allowed, count, remaining, reason) or a PacingState. Run the built-in demo against a live endpoint with python -m temporalstore.control_state.

Getting it right in production

Atomicity, durability & idempotency

A single-key counter update is atomic — the increment and the window read run as one command on one object, so no two requests race past a cap. Choose durability by how costly a lost write is:

ModeWhenTrade-off
Async (default)High-QPS controls — caps, quotas, pacingAcknowledges fast; the commit is durable within the configured lag.
SyncState that must survive node loss before ackBlocks on fsync; use selectively for critical keys.
Idempotency for queue replay. With at-least-once delivery, attach a uuid and commit the processed offset only after the durability threshold is met. The dedup ledger keeps a 5-minute window, matching the reference semantics, so retries don't inflate a cap or a quota.
Cache eviction is not deletion. A hot key evicted from memory stays recoverable from durable storage until its window expires and compaction reclaims it. Keep current-value state with a TTL, not an append-only debug log.

  • Store current-value state with a TTL, never an append-only history.
  • Make single-key counter updates atomic; use HSETANDGET for accept-decisions.
  • Require a uuid when replaying from a durable queue.
  • Keep high-QPS controls async by default; reserve sync for state that must survive node loss.
  • Distinguish API acknowledgement, append acceptance, and durable persistence.

What shipped

The idempotency primitive & the perf finding

Delivered

Replay-safe atomic op

ControlStateSetAndGetWithOptions — precision + TTL + uuid dedup + change aggregator. Reachable via HSETANDGETOPT and the typed client, with parity tests for precision bucketing and idempotent replay.

Finding

Write-path scaling

The live write path runs a per-command slot-index promotion that is O(live keyspace), so per-op latency grows with the working set. A safe deferral needs the flush/reconcile path — flagged as a scoped follow-up, not a claimed fix.
