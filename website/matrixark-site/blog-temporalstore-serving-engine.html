TemporalStore Essay

Why temporal features need a serving engine, not just another cache.

The next generation of online decision systems needs fresh, explainable, replayable temporal state. That is a different problem from storing a value under a key.

The short version

Fraud, ads, recommendation, personalization, and AI agent systems increasingly depend on questions like: how many times did this device fail login in the last 30 minutes, which merchants did this card touch in the last 24 hours, what did this user recently read, and which policy counters should shape the next model call?

A cache can hold the answer after something else computes it. A stream processor can precompute a few known windows. A feature store can materialize the latest value. But fast-changing online products need a serving engine that understands the temporal shape of the data itself: windows, filters, distinct counts, sequences, freshness, replay, and persistence.

TemporalStore is MatrixArk's answer to that gap. It is designed as an online temporal state engine: ingest events and profile updates, keep hot model-aware objects in memory, persist replayable state, and serve temporal queries directly in the request path.

The problem with cache-plus-pipeline architectures

Many teams start with a reasonable architecture: stream events into a processor, compute aggregates, write the result into a cache or online store, and let the application read the latest value. This works well when the feature set is stable and the query shape is simple.

It becomes painful when product rules move faster than the pipelines. Risk teams add new velocity checks. Ads teams change frequency windows. Recommendation teams want more recent sequence slices. Agent systems need session context and policy state that changes while a user is interacting. Every new temporal question turns into a new pipeline, a new key layout, a new expiry policy, and another place where training and serving semantics can drift.

The core issue: plain KV systems store values, but temporal products need storage to understand how those values were produced, when they are valid, and how to query the event state behind them.

What a temporal serving engine should own

TemporalStore puts the temporal data model inside the serving engine. Instead of treating a value as an opaque blob, the engine understands the object type and the operations that are valid for that object.

Temporal counters

Increment and query event counts or sums over windows, such as purchases in five minutes or impressions in one hour.

Filtered aggregates

Aggregate only the subset that matches dimensions such as country, merchant category, campaign, device, or action type.

Distinct state

Answer questions such as unique merchants, unique IPs, unique devices, or unique campaigns in a recent time range.

Long sequences

Serve recent behavior history, ordered events, and model input sequences without scattering sequence logic across services.

Profiles and latest state

Keep latest profile fields near temporal state when the online decision needs both.

Structured AI context

Store session timelines, tool events, policy counters, user preferences, and context metadata beside vector retrieval systems.

The architecture pattern

The important architectural idea is not just "put data in memory." The important idea is to combine hot state, model-aware updates, a replayable log, and page-oriented persistence behind one serving API.

Client / stream writer Router Partition worker Model engine WAL / oplog Page and index store Window query

A write is routed by namespace, table, model, and key. The owning partition worker updates the in-memory object, records the mutation, and marks the relevant object state dirty for persistence. A read resolves the same model and asks the engine for a window, filter, sequence, distinct count, latest profile, or combined view.

This shape is intentionally different from a generic database query engine. The engine is optimized for online decisions over entity-local temporal state. It does not try to be a warehouse, and it does not try to replace vector search. It is the low-latency state body around those systems.

Why not only offline aggregation?

Offline aggregation is still essential for training, reporting, backfills, and long-term analytics. TemporalStore is not trying to replace the warehouse. The point is that some decisions cannot wait for the next offline job, and some product questions are too dynamic to justify building a new batch or streaming pipeline first.

A good production architecture can use both. Offline systems compute durable historical truth. TemporalStore serves fresh online state and can export logs or snapshots back into the training and analytics path. The product boundary is simple: if the question is needed inside the request path and depends on recent entity-local state, it belongs close to the online serving engine.

How this compares with Redis, feature stores, and stream processors

Redis-style systems are excellent general-purpose caches and often the right choice for plain strings, hashes, and latest-value serving. MatrixDB exists for that side of the MatrixArk platform. TemporalStore is different: it is for temporal semantics, model-aware operations, and high-cardinality windows.

Feature stores are excellent at registry, discovery, offline/online consistency, and materialization workflows. TemporalStore can sit underneath them as an online temporal store. It does not need to own the whole feature platform to be useful.

Stream processors are excellent for known real-time transformations. TemporalStore reduces the number of cases where every new temporal question requires a new streaming topology before the product can ship.

The open-source path

The clean open-source version should start with a single-node engine. Distributed systems become much easier to trust once the local model semantics, WAL, snapshots, page format, metrics, and SDKs are correct.

  1. Single-node TemporalStore with HTTP/gRPC APIs, local WAL, snapshots, and model-aware queries.
  2. Python and Go SDKs for risk, feature serving, and AI context examples.
  3. Local Docker Compose and Prometheus metrics so users can try it quickly.
  4. Primary-replica log shipping for distributed mode.
  5. Raft mode later for partitions that require stronger consistency guarantees.

The first version does not need to claim it replaces every cache, database, or feature platform. It only needs to be very good at one painful thing: serving fresh temporal state for high-cardinality online decisions.

Where TemporalStore fits in MatrixArk

MatrixArk is a product matrix, not a single monolithic database. TemporalStore handles temporal state. MatrixDB handles plain distributed KV and Redis-compatible profile serving. MatrixKV handles correctness-sensitive metadata and control-plane state.

That separation is the product strategy. It lets each engine be honest about what it is good at while still giving customers one operating surface for deployment, observability, SDKs, and cloud management.
