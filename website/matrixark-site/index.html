Platform Thesis

Three serving engines. One real-time data platform.

Most production teams stitch together stream jobs, caches, online stores, offline materialization, custom serving services, and control-plane databases. MatrixArk narrows that stack into purpose-built engines for the online path.

TemporalStore Fresh entity state

Rolling windows, frequency caps, long sequences, structured context, and risk signals.

ABase Large-scale KV

Distributed key-value and profile serving with a Redis-compatible migration path.

ByteKV Consistent core

Strongly consistent KV for metadata, leases, routing state, and transactional control paths.

Products

Designed around workload fit, not one generic database claim.

T

TemporalStore

Online temporal feature and context serving for high-cardinality entities, arbitrary windows, filtered aggregates, long sequences, and persisted state.

  • TemporalCounter, TemporalAggregate, TemporalDistinct, SequenceModel, Hash/KV
  • Storage-side filtering, aggregation, sorting, deduplication, and model logic
  • Hot in-memory objects with page/index/oplog persistence design
A

ABase

Distributed KV and Redis-compatible online serving for profiles, hashes, strings, high-QPS lookups, and cache-plus-storage workloads.

  • Dual Redis and Thrift listener path validated in AWS smoke tests
  • Best current write/mixed plain-KV baseline among the measured services
  • Designed as the broader distributed KV expansion path
K

ByteKV

Strongly consistent distributed KV foundation for metadata, configuration, leases, coordination state, and infrastructure control planes.

  • Raft-style consistency foundation for system state
  • Good fit for transactional metadata and routing/control-plane records
  • Complements TemporalStore and ABase rather than replacing them

TemporalStore write path

  1. Route key to the primary partition.
  2. Apply model-specific update to hot object state.
  3. Append mutation log and mark dirty slot/page state.
  4. Dump merged pages and replayable state in the background.

TemporalStore read path

  1. Resolve table, partition, and model.
  2. Use in-memory index to locate object or persisted page.
  3. Serve hot state or load through block/page cache.
  4. Run storage-side window, filter, sequence, or aggregate logic.

Market Position

Feature platform feel, infrastructure-engine depth.

Chalk-style feature platforms emphasize defining features once, serving them at low latency, and reducing training-serving drift. Redis-style enterprise offerings emphasize compatibility, scale, and managed operations. MatrixArk should sit between them: a storage-engine platform for the online state that those systems depend on.

Compared with feature stores

MatrixArk does not need to replace the registry or offline warehouse first. It becomes the online temporal serving engine under Feast, feature platforms, risk engines, and inference systems.

Compared with Redis Enterprise

Redis is excellent for mature general-purpose cache workloads. TemporalStore is specialized for high-cardinality temporal windows, long sequences, filtered state, and persisted online features.

Compared with generic KV

ABase and ByteKV cover broader KV paths, while TemporalStore keeps model-aware computation inside the serving engine for risk, ads, recommendations, and AI context.
